# Архитектура quakke-video

## Подход

Проект строится как modular monolith с отдельными worker-приложениями. Бизнес-модули
живут внутри одного NestJS API и общаются через явные публичные интерфейсы. Тяжелые и
асинхронные операции выполняются воркерами через RabbitMQ.

## Runtime-приложения

- `web` - публичный пользовательский видеохостинг.
- `studio` - рабочее место автора.
- `admin` - административная панель.
- `api` - GraphQL API для бизнес-данных и REST для upload, health и технических endpoint.
- `worker-media` - FFmpeg, HLS, превью и обработка медиа.
- `worker-notifications` - email и внутренние уведомления.

## Хранилища и транспорт

- PostgreSQL является источником истины для бизнес-данных.
- Redis хранит только кеш и временные данные; он не является источником истины.
- RabbitMQ доставляет фоновые задания с семантикой at-least-once.
- MinIO используется только как локальный S3-совместимый стенд. Production provider
  выбирается отдельно и подключается через S3 adapter.

## Границы

- Приложения могут зависеть от shared-пакетов, но не друг от друга.
- `contracts` содержит только переносимые схемы и типы на границах системы.
- `api-client` инкапсулирует сетевое взаимодействие frontend-приложений с API.
- `ui` не содержит продуктовой бизнес-логики.
- Worker не вызывает внутренности API напрямую: входом служит контракт сообщения,
  результат сохраняется через устойчивый adapter и публикуется как событие.

## Надежность фоновых задач

Consumer обязан быть идемпотентным. Сообщение подтверждается только после успешного
завершения операции. Для временных ошибок используются ограниченные retry и delay,
для неисправимых сообщений - dead-letter queue. Correlation ID проходит через API,
очередь и логи.
